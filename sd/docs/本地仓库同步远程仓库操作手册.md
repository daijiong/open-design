# 本地仓库同步远程仓库操作手册

本文档说明如何让本地仓库、自己 GitHub 账号下的仓库、原始开源仓库保持一致。

当前项目远程仓库约定：

- `origin`：自己账号下的仓库，用于日常推送。
- `upstream`：原始开源仓库，用于拉取官方最新代码。

当前仓库配置：

```text
origin   https://github.com/daijiong/open-design.git
upstream https://github.com/nexu-io/open-design.git
```

## 1. 查看远程仓库配置

在仓库根目录执行：

```powershell
git remote -v
```

预期能看到：

```text
origin    https://github.com/daijiong/open-design.git (fetch)
origin    https://github.com/daijiong/open-design.git (push)
upstream  https://github.com/nexu-io/open-design.git (fetch)
upstream  DISABLED (push)
```

说明：

- `origin` 是自己的仓库，可以推送。
- `upstream` 是原始仓库，只用于拉取，不用于推送。
- `upstream` 的 push 地址设为 `DISABLED`，是为了避免误推到原始仓库。

## 2. 日常同步流程

目标：把原始仓库 `upstream/main` 的最新代码同步到本地 `main`，再推送到自己的 `origin/main`。

### 第一步：切换到 main 分支

```powershell
git switch main
```

作用：确保当前操作的是主分支。

### 第二步：拉取原始仓库最新引用

```powershell
git fetch upstream
```

作用：从原始仓库获取最新提交、分支和标签。

注意：这一步只更新本地的远程引用，不会直接修改当前工作区代码。

### 第三步：合并原始仓库 main 分支

```powershell
git merge upstream/main
```

作用：把原始仓库最新代码合并到本地 `main` 分支。

如果没有冲突，Git 会自动完成合并。

### 第四步：推送到自己的 GitHub 仓库

```powershell
git push origin main
```

作用：把同步后的本地 `main` 推送到自己账号下的远程仓库。

## 3. 推荐的完整命令

```powershell
git switch main
git fetch upstream
git merge upstream/main
git push origin main
```

数据流向如下：

```text
原始仓库 upstream/main
        ↓
本地仓库 main
        ↓
自己仓库 origin/main
```

## 4. 同步前检查本地是否有改动

同步前建议先执行：

```powershell
git status --short --branch
```

如果看到未提交改动，例如：

```text
 M some-file.ts
?? new-file.md
```

说明本地工作区不干净。

处理方式有两种：

### 方式一：提交本地改动

```powershell
git add .
git commit -m "描述本次改动"
```

提交后再执行同步流程。

### 方式二：临时保存本地改动

```powershell
git stash push -m "同步前临时保存"
```

同步完成后恢复：

```powershell
git stash pop
```

## 5. 遇到冲突时怎么处理

如果执行：

```powershell
git merge upstream/main
```

后出现冲突，Git 会提示哪些文件冲突。

查看冲突文件：

```powershell
git status
```

打开冲突文件，找到类似内容：

```text
<<<<<<< HEAD
本地内容
=======
远程内容
>>>>>>> upstream/main
```

手动保留正确内容，并删除这些冲突标记。

处理完后执行：

```powershell
git add 冲突文件路径
git commit
```

最后再推送：

```powershell
git push origin main
```

## 6. 本次冲突处理实战流程

当本地改动和 `upstream/main` 的改动都要保留时，不要简单执行 `git checkout --ours` 或 `git checkout --theirs` 覆盖文件，而是逐个文件合并语义。

### 第一步：查看未解决冲突文件

```powershell
git diff --name-only --diff-filter=U
```

这条命令只列出仍处于冲突状态的文件。

也可以查看完整状态：

```powershell
git status --short
```

状态里出现 `UU` 的文件就是未解决冲突文件。

### 第二步：定位冲突标记

```powershell
rg -n "<<<<<<<|=======|>>>>>>>" apps packages
```

说明：

- `<<<<<<< HEAD` 下面是合并前本地分支的内容。
- `=======` 是本地内容和远程内容的分隔线。
- `>>>>>>> upstream/main` 上面是远程 `upstream/main` 的内容。

注意：文档示例中也可能包含这些标记，排查代码冲突时建议限制目录范围，例如只查 `apps`、`packages`。

### 第三步：按语义合并，而不是二选一

本次冲突的处理原则：

- 本地已有的登录、用户、权限、管理员限制要保留。
- 远程新增的插件、市场、plugin snapshot、workspace UI、tool-result 能力也要保留。
- 如果两边改的是同一个对象，要把字段、参数、props、导出项合并完整。
- 如果两边改的是同一个路由，要确认鉴权、项目访问校验、远程新增逻辑都还在。

示例：如果本地新增了 `auth` 导出，远程新增了 `plugins` 导出，最终应该同时保留：

```ts
export * from './api/auth.js';
export * from './plugins/index.js';
```

### 第四步：确认冲突标记已清理

```powershell
git diff --name-only --diff-filter=U
```

如果没有输出，说明 Git 层面已经没有未解决冲突。

再检查代码中的冲突标记：

```powershell
rg -n "<<<<<<<|=======|>>>>>>>" apps packages
```

### 第五步：上游新增依赖后刷新 workspace

如果远程合并进来新增了 workspace 包、依赖或 contracts 导出，建议执行：

```powershell
$node24='C:\Users\Administrator\AppData\Local\nvm\v24.15.0'
& "$node24\node.exe" "$node24\node_modules\corepack\dist\pnpm.js" install
```

说明：这里是临时指定 Node 24 执行命令，不会修改本机默认 Node 版本。

### 第六步：运行验证

本次冲突处理后执行过的核心验证：

```powershell
$node24='C:\Users\Administrator\AppData\Local\nvm\v24.15.0'

& "$node24\node.exe" "$node24\node_modules\corepack\dist\pnpm.js" --filter @open-design/contracts typecheck
& "$node24\node.exe" "$node24\node_modules\corepack\dist\pnpm.js" --filter @open-design/daemon build
& "$node24\node.exe" "$node24\node_modules\corepack\dist\pnpm.js" --filter @open-design/web typecheck
& "$node24\node.exe" "$node24\node_modules\corepack\dist\pnpm.js" --filter @open-design/web exec vitest run -c vitest.config.ts tests/components/App.connectors.test.tsx
```

### 第七步：标记冲突已解决

只添加已经确认处理完成的冲突文件：

```powershell
git add apps/daemon/src/chat-routes.ts
git add apps/daemon/src/db.ts
git add apps/daemon/src/project-routes.ts
git add apps/daemon/src/server.ts
git add apps/web/src/App.tsx
git add apps/web/src/components/EntryView.tsx
git add apps/web/src/components/SettingsDialog.tsx
git add apps/web/tests/components/App.connectors.test.tsx
git add packages/contracts/src/index.ts
```

如果解决冲突时为了兼容两边改动而新增或修改了相关文件，也要一起添加。例如本次为了让新版入口页继续显示当前用户和退出登录，补充了：

```powershell
git add apps/web/src/components/EntryShell.tsx
```

### 第八步：提交 merge

确认没有未解决冲突：

```powershell
git diff --name-only --diff-filter=U
```

提交合并：

```powershell
git commit --no-edit
```

`--no-edit` 表示使用 Git 自动生成的 merge commit message。

### 第九步：推送自己的远程仓库

```powershell
git push origin main
```

推送后，自己 GitHub 仓库的 `main` 就包含了本地改动和原始仓库最新改动。

## 7. 只想查看原始仓库有没有更新

如果只想查看是否有新提交，不想立即合并：

```powershell
git fetch upstream
git log --oneline main..upstream/main
```

如果有输出，说明原始仓库有本地还没有的提交。

如果没有输出，说明本地 `main` 已经包含原始仓库 `main` 的最新提交。

## 8. 不推荐直接使用 reset

不建议随意执行：

```powershell
git reset --hard upstream/main
```

原因：它会强制把本地代码改成原始仓库状态，可能丢失本地提交或未保存改动。

只有在明确要完全丢弃本地差异时，才考虑使用强制重置。

## 9. 常用排查命令

查看当前分支和工作区状态：

```powershell
git status --short --branch
```

查看远程仓库：

```powershell
git remote -v
```

查看当前分支提交历史：

```powershell
git log --oneline --decorate -10
```

查看本地 main 比 upstream/main 多了哪些提交：

```powershell
git log --oneline upstream/main..main
```

查看 upstream/main 比本地 main 多了哪些提交：

```powershell
git log --oneline main..upstream/main
```
