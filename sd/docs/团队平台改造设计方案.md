# Open Design 团队平台改造设计方案

编写日期：2026-05-14

## 1. 目标与范围

本方案把当前偏单用户、本地优先的 Open Design 改造成团队成员可共同使用的平台。改造目标有三点：

- 团队成员可以自行注册、登录，并进入与当前网站风格一致的工作台。
- 普通成员只能看到、创建、编辑自己的设计项目。
- 管理员可以看到所有成员的设计，并且只有管理员可以修改网站级配置。

本方案聚焦产品设计、技术架构、权限模型、数据结构、接口边界和实施步骤，不直接包含代码实现。

## 2. 当前系统判断

根据现有代码和文档，当前系统的关键事实如下：

- `apps/web` 是 Next.js + React 前端，主工作台入口在 `apps/web/src/App.tsx` 与 `EntryView`。
- `apps/daemon` 是 Express + SQLite 本地 daemon，负责 REST/SSE API、项目持久化、agent 调用、设计系统、技能、制品和配置。
- 当前 `projects/conversations/messages/tabs` 等数据存在 SQLite 中，项目文件在 `.od/projects/<projectId>/` 或导入文件夹中。
- 当前 `docs/spec.md` 明确把 Auth/Orgs/Multi-user 排除在 MVP 外，因此多用户能力需要作为新的平台层补齐。
- 当前网站视觉是中性产品工作台风格：浅色米白背景、白色面板、细边框、克制阴影、暖橙色主行动色、深色模式共用变量。

关键结论：不要只在前端隐藏按钮。必须在 daemon/API 层做认证、项目归属过滤和管理员权限校验，否则普通用户可以绕过 UI 直接访问或修改数据。

## 3. 关键假设

- 第一阶段采用“单团队平台”模型：所有注册用户默认属于同一个团队，不先做多组织、多租户和计费。
- 账号体系由平台自己维护，使用邮箱 + 密码登录；后续可扩展企业 SSO。
- 初始管理员通过部署环境变量或初始化脚本创建，避免第一个注册用户自动成为管理员带来的风险。
- 团队共用一套 agent、模型、设计系统、技能和媒体配置；这些配置只有管理员可改。
- 设计项目默认私有：普通用户只看自己的项目，管理员看全站项目。
- 本轮不做多人实时协同编辑；团队成员“共同使用”指共享同一个平台实例和统一配置，而不是同时编辑同一个设计文件。

需要确认的问题：

- 是否允许管理员“代替普通用户编辑/删除项目”，还是只读查看即可。
- 是否需要邀请制注册，还是开放注册后由管理员停用/授权。
- 是否需要团队成员之间主动分享某个设计项目。如果需要，应在第二阶段增加项目协作者表。

## 4. 用户角色与权限模型

系统只先定义两个角色：

| 角色 | 可见设计 | 可用功能 | 配置权限 |
|---|---|---|---|
| 普通用户 `member` | 只看到自己创建的项目 | 创建设计、继续对话、上传设计文件、导出、删除自己的项目 | 无 |
| 管理员 `admin` | 可以看到所有用户的项目 | 普通用户全部能力；可按用户筛选项目；可管理用户状态 | 有 |

权限规则：

- `GET /api/projects`：普通用户返回 `owner_user_id = 当前用户` 的项目；管理员返回全部项目。
- `GET/PATCH/DELETE /api/projects/:id`：普通用户只能操作自己的项目；管理员可访问全部项目。
- 项目下的 conversations、messages、tabs、preview comments、deployments、artifact files 都继承项目权限。
- 所有网站配置接口必须要求管理员角色，包括 `app-config`、媒体模型配置、连接器配置、技能启停、设计系统启停、Orbit/Routines 等。
- 普通用户打开 Settings 时只显示个人偏好类项目，例如语言、外观、通知；隐藏或禁用执行环境、模型、API key、连接器、技能、设计系统等站点级配置。

## 5. 登录与注册页面设计

### 5.1 视觉原则

登录注册页应延续当前工作台风格，而不是做营销型落地页：

- 背景使用现有 `--bg` / `--bg-app` 的中性米白或深色模式变量。
- 表单容器使用 `--bg-panel`、`--border`、`--shadow-sm`，边角保持 8-12px。
- 主按钮使用现有暖橙 `--accent`，选中/输入 focus 继续使用当前系统的克制蓝色或细描边。
- 左上角保留 Open Design 品牌标识，右上角可放语言/主题切换。
- 页面主体是登录/注册表单，不做大幅 hero 和装饰插画。

### 5.2 页面布局

建议新增 `/login` 与 `/register` 两个路由，也可内部复用一个 `AuthPage` 组件。

桌面端布局：

- 顶部窄 chrome：品牌、语言、主题。
- 中间 360-420px 宽表单面板。
- 面板内包含标题、说明、字段、主按钮、错误提示、切换登录/注册入口。
- 面板底部显示平台域名或版本信息，便于团队成员确认登录的是公司实例。

移动端布局：

- 表单面板不悬浮，使用全宽内边距。
- 字段高度保持 40-44px，按钮不换行。
- 错误提示紧贴字段下方，不使用全屏 toast 承载关键错误。

### 5.3 登录表单字段

- 邮箱
- 密码
- “保持登录”勾选项
- 登录按钮
- 注册入口
- 忘记密码入口可先预留，第一阶段可以显示“请联系管理员重置”

### 5.4 注册表单字段

- 姓名
- 邮箱
- 密码
- 确认密码
- 注册按钮
- 已有账号登录入口

注册成功后的策略建议：

- 如果采用开放注册：注册后直接进入普通用户工作台。
- 如果采用邀请/审核：注册后进入“等待管理员启用”的只读状态。

## 6. 数据模型改造

### 6.1 新增用户表

建议在 SQLite 中新增 `users` 表：

```sql
CREATE TABLE users (
  id TEXT PRIMARY KEY,
  email TEXT NOT NULL UNIQUE,
  name TEXT NOT NULL,
  password_hash TEXT NOT NULL,
  role TEXT NOT NULL CHECK (role IN ('admin', 'member')),
  status TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active', 'disabled', 'pending')),
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  last_login_at INTEGER
);
```

### 6.2 新增会话表

```sql
CREATE TABLE sessions (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL,
  token_hash TEXT NOT NULL UNIQUE,
  expires_at INTEGER NOT NULL,
  created_at INTEGER NOT NULL,
  last_seen_at INTEGER,
  FOREIGN KEY(user_id) REFERENCES users(id) ON DELETE CASCADE
);
```

会话 token 只以 HttpOnly Cookie 下发，数据库只保存 hash。

### 6.3 项目表增加归属字段

`projects` 表新增：

```sql
ALTER TABLE projects ADD COLUMN owner_user_id TEXT;
CREATE INDEX idx_projects_owner_updated ON projects(owner_user_id, updated_at DESC);
```

迁移策略：

- 对已有项目，把 `owner_user_id` 赋给初始化管理员。
- 后续创建项目时，daemon 从当前登录用户写入 `owner_user_id`，前端不能提交该字段。

### 6.4 配置拆分

当前 `app-config.json` 是全局偏好与配置混在一起。团队平台建议拆成两类：

- 网站级配置：agent、模型、API key、媒体 provider、连接器、技能启停、设计系统启停、Orbit/Routines。只允许管理员读写。
- 用户级偏好：语言、主题、通知、pet 显示、个人最近选择。普通用户可读写自己的偏好。

推荐新增 `user_preferences` 表：

```sql
CREATE TABLE user_preferences (
  user_id TEXT PRIMARY KEY,
  prefs_json TEXT NOT NULL,
  updated_at INTEGER NOT NULL,
  FOREIGN KEY(user_id) REFERENCES users(id) ON DELETE CASCADE
);
```

第一阶段也可以继续保留部分浏览器 localStorage 偏好，但涉及权限和团队一致性的配置必须迁到 daemon 端。

## 7. API 改造方案

### 7.1 新增认证接口

- `POST /api/auth/register`
  - 入参：`name/email/password`
  - 出参：当前用户基础信息
  - 行为：创建普通用户或 pending 用户

- `POST /api/auth/login`
  - 入参：`email/password/remember`
  - 行为：校验密码，写入 session，设置 HttpOnly Cookie

- `POST /api/auth/logout`
  - 行为：删除当前 session，清除 Cookie

- `GET /api/auth/me`
  - 出参：`id/name/email/role/status`
  - 前端启动时用于判断是否进入工作台或登录页

### 7.2 项目接口增加用户上下文

所有项目接口统一使用认证中间件：

- 未登录返回 `401 AUTH_REQUIRED`
- 登录但无权限返回 `403 FORBIDDEN`
- 普通用户访问其他人的项目返回 `404 PROJECT_NOT_FOUND` 或 `403 FORBIDDEN`。为减少信息泄露，建议用 `404`。

项目列表返回结构建议增加 owner 信息，仅管理员可见：

```ts
interface Project {
  id: string;
  name: string;
  ownerUserId?: string;
  ownerName?: string;
  ownerEmail?: string;
  ...
}
```

### 7.3 管理员配置接口

对以下接口统一加 `requireAdmin`：

- `GET/PUT /api/app-config`
- `GET/PUT /api/media/config`
- 连接器配置接口
- 技能启用/禁用、创建、删除接口
- 设计系统启用/禁用接口
- Routines/Orbit 配置接口
- 后续用户管理接口

普通用户如果调用这些接口，返回：

```json
{
  "error": {
    "code": "ADMIN_REQUIRED",
    "message": "Only administrators can change site settings."
  }
}
```

### 7.4 管理员用户管理接口

第一阶段建议提供：

- `GET /api/admin/users`
- `PATCH /api/admin/users/:id`
  - 修改 `name/role/status`
- `POST /api/admin/users/:id/reset-password`
  - 生成临时密码或重置链接

这些接口全部要求 `admin`。

## 8. 前端改造方案

### 8.1 路由与启动流程

`App` 启动时先请求 `/api/auth/me`：

- `200` 且用户 active：加载配置、项目和工作台。
- `401`：跳转 `/login`。
- `200` 但用户 pending/disabled：显示账号状态页。

### 8.2 工作台变化

普通用户：

- 首页 Designs 标题仍为 “Your designs”。
- 不显示其他用户筛选器。
- Settings 中只显示个人偏好 section。
- 创建项目时无需感知 owner，后端自动绑定。

管理员：

- 首页 Designs 增加筛选控件：全部用户 / 指定用户 / 只看自己。
- 项目卡片显示 owner 名称或邮箱。
- Settings 显示完整配置项。
- 增加 “Users” 管理入口，可放在 Settings 侧边栏。

### 8.3 组件建议

新增：

- `AuthPage.tsx`
- `LoginForm.tsx`
- `RegisterForm.tsx`
- `AuthProvider.tsx`
- `AdminUsersSection.tsx`

改造：

- `App.tsx`：接入登录态、角色态和启动分支。
- `EntryView.tsx` / `DesignsTab.tsx`：管理员项目筛选和 owner 展示。
- `SettingsDialog.tsx`：按角色过滤 section。
- `state/projects.ts`：保持现有 API 形状，处理 401/403。
- `state/config.ts`：普通用户只同步个人偏好，管理员同步站点配置。

## 9. Daemon 与部署形态调整

当前 daemon 默认信任本机调用。团队平台部署后，daemon 会成为多人共享服务，必须加强边界：

- 所有 `/api/*` 默认要求认证，健康检查、版本、登录注册接口除外。
- Cookie 使用 `HttpOnly; SameSite=Lax; Secure`，本地开发可关闭 Secure。
- 对登录、注册、密码重置加速率限制。
- 密码使用 `argon2id` 或 `bcrypt` 哈希，禁止明文或可逆加密。
- 管理员 API 不依赖前端隐藏入口，必须服务端校验角色。
- 对 SSE/chat run 也要校验项目 owner，防止订阅他人项目事件。
- 项目文件访问、artifact 静态服务、下载 ZIP/PDF 都要通过项目权限校验。

特别注意：如果允许团队共享同一个本地 agent CLI，所有用户的设计生成都会运行在同一个服务器环境中。后续如果要严格隔离执行环境，需要把 agent run 放进每用户 workspace 或容器中。

## 10. 安全与审计

第一阶段必须做：

- 密码复杂度基础校验：最少 8 位，建议包含字母和数字。
- 登录失败限流：按 IP + email 限制。
- 会话过期：默认 7 天，勾选保持登录可延长到 30 天。
- 用户停用后立即清理其 session。
- 管理员降级自己时需要阻止最后一个管理员被移除。
- API key 和 provider secret 只允许管理员写入，普通用户不返回明文或尾号。
- 项目文件路径继续保持现有 realpath/path traversal 防护。

建议第二阶段增加：

- `audit_logs` 表，记录登录、配置变更、角色变更、删除项目、导出等动作。
- 管理员查看所有项目时记录访问日志。
- 邀请链接和邮件验证。

## 11. 实施计划

### 阶段 1：认证基础

目标：用户能注册、登录、退出，系统能识别当前用户和角色。

工作项：

- 新增 `users/sessions/user_preferences` 表和迁移。
- 新增认证中间件：`requireAuth`、`requireAdmin`。
- 新增 `/api/auth/register/login/logout/me`。
- 新增登录注册页面，并接入启动流程。

验证方式：

- 未登录访问工作台会进入登录页。
- 注册后可以登录。
- Cookie 为 HttpOnly。
- 停用用户不能登录。

### 阶段 2：设计项目隔离

目标：普通用户只能看到自己的设计，管理员能看到所有设计。

工作项：

- `projects` 增加 `owner_user_id`。
- 创建项目时自动绑定当前用户。
- 所有项目、会话、消息、文件、导出、事件订阅接口做 owner 校验。
- 管理员项目列表增加 owner 展示和筛选。

验证方式：

- 用户 A 创建项目，用户 B 的列表不可见。
- 用户 B 直接请求用户 A 的项目详情返回 404/403。
- 管理员能看到 A/B 的项目并按 owner 筛选。

### 阶段 3：管理员配置权限

目标：只有管理员能改网站级配置。

工作项：

- 梳理 Settings 中所有站点级配置。
- 后端给配置类接口加 `requireAdmin`。
- 前端按角色过滤 Settings section。
- 普通用户保留语言、外观、通知等个人偏好。

验证方式：

- 普通用户界面看不到站点配置。
- 普通用户直接调用配置接口返回 `ADMIN_REQUIRED`。
- 管理员修改配置后，普通用户后续生成使用新配置。

### 阶段 4：管理员用户管理

目标：管理员可维护团队成员账号。

工作项：

- 新增 Settings → Users 页面。
- 支持查看用户、禁用用户、调整角色、重置密码。
- 防止删除或降级最后一个管理员。

验证方式：

- 管理员能禁用普通用户。
- 被禁用用户的 session 失效。
- 系统始终至少保留一个 active admin。

## 12. 测试策略

后端测试：

- 认证接口：注册、登录、退出、错误密码、停用用户。
- 项目隔离：list/get/patch/delete/conversations/messages/files/export/events。
- 管理员权限：配置接口和用户管理接口。
- 迁移测试：旧项目归属初始化管理员。

前端测试：

- 登录注册表单校验。
- 未登录跳转。
- 普通用户 Settings section 过滤。
- 管理员 Designs owner 筛选。

端到端测试：

- 两个普通用户 + 一个管理员的完整流程。
- 普通用户绕过 UI 访问他人项目失败。
- 管理员配置模型后普通用户可以正常创建设计。

建议命令边界仍遵守仓库现有规则：

```powershell
pnpm guard
pnpm typecheck
pnpm --filter @open-design/web test
pnpm --filter @open-design/daemon test
```

## 13. 风险与取舍

- 如果只做前端页面和隐藏按钮，数据隔离是不成立的；必须从 daemon API 层改。
- 当前配置体系有全局配置和浏览器本地偏好混用，团队化后要明确哪些是站点配置、哪些是个人偏好。
- `.od/projects/<id>` 是共享磁盘目录，普通用户不能通过静态路径直接下载他人文件，所有文件服务都必须走权限校验。
- 团队共享 agent/API key 简化了第一阶段，但成本、额度和执行隔离都由管理员承担。
- 项目协作者和项目分享很有价值，但会扩大权限矩阵，建议第二阶段再做。

## 14. 建议的最终体验

普通成员打开网站后：

1. 进入登录页或注册页。
2. 登录后看到自己的 Designs、Templates、Design Systems 浏览入口。
3. 可以创建、继续编辑、导出自己的设计。
4. Settings 中只能调整个人体验偏好。

管理员打开网站后：

1. 登录后看到所有设计，并能按成员筛选。
2. 项目卡片上能看到创建者。
3. Settings 中可以配置模型、agent、API key、连接器、技能、设计系统和用户。
4. 可以停用用户、调整角色、重置密码。

这样改造后，系统会从“单机个人设计工具”升级为“团队共享设计生成平台”，同时保持当前 Open Design 的产品工作台风格和本地 daemon 驱动的核心能力。
